Using Dependence DAGs, its possible to represent computations as nodes and dependencies as edges. Each node has a weight for time, so the work required for the program on one processor is the sum of all weights, \(T_1\). Span (or critical path) is the path with the largest weight. The path weight is \(T_\inf\), and this is the baseline that any scheduling can't improve on.

\(\operatorname{IP}(t)\), instantaneous parallel, is the maximum number of processors that can be busy at \(t\). Maximal parallelism \(\mathnormal{MP}\) is the highest instantaneous parallelism. Average parallelism \(\mathnormal{AP} = \frac{T_1}{T_\inf}\). 

By introducing more processors into execution, there is \(\operatorname{Speed-up}(P)\). Performance can theoretically be more than \(P\) times, but it is restricted by \(T_\inf\). Another way to describe it is with Amdahl's law; let \(p%\) of the program be able to be done in parallel, then the \(\operatorname{Speed-up} \leq \frac{1}{1 - p}\) (i.e., work divided by span).

Dependencies and multiple processors makes schedule matter. If the DAG is a tree, the optimal schedule is level-by-level. But in general, use the critical path as a heuristic. Nodes are given priorities, and the earlier a node is on the critical path is given an even higher priority.

The DAGs are generated by looking at the dependencies from the compiler. This means data dependencies. Conservative approximation and its interaction with aliasing generates the most imprecisions. There are transformations to reduce the number of may-aliasing scenarios by the compiler.

Static scheduling makes a load of assumptions about the work for various instructions. This is fine for a large portion of instructions, but some (e.g., load) introduce variability in latency.
